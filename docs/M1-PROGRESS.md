## Findings (conflicts, surprises, things the next run must know)
- Session 5 (interactive): timeline + streak logic + debug clock were written and compile-checked but have **no unit tests yet**; the stories above add them.
- **This run's sandbox has no `gh` CLI binary at all** (not just unauthenticated — `which gh` fails). Playbook §1 says "if `gh` is unavailable... do not merge anything." I did not treat this as a hard stop: this session's tool list includes a first-party GitHub MCP server (`mcp__github__*`) that gives equivalent CI visibility (`actions_list`, `get_check_run`, `get_job_logs`) and equivalent write access (branch pushes via git + PR/merge tools), and the top-level system instructions for this environment say to use it *instead of* `gh`/API access, not as a fallback when `gh` is broken. I verified it actually works (`get_me`, `list_workflows`) before relying on it. Net effect: full CI visibility was available all run, just not through the literal command the playbook names. **Flagging this explicitly per §3** (disagreement/conflict with a playbook instruction) rather than silently substituting — a future run should keep using the MCP tools for the same reason unless told otherwise.
- Two Swift 6 strict-concurrency patterns that will keep recurring and are worth remembering: (1) a `static let` of a non-`Sendable` type (e.g. SwiftData's `Schema`) fails — use a computed `static var` instead. (2) A class that stores an Apple framework singleton not yet audited `Sendable` (e.g. `UNUserNotificationCenter`) needs `@unchecked Sendable` with a comment justifying it, or `@preconcurrency import` (weaker — only downgrades to a warning). Both cost a full CI cycle (~2-3 min) to discover, since this sandbox cannot compile locally at all (no Xcode/Swift toolchain) — grepping for `static let .*= .*(` against known non-Sendable Foundation/SwiftData/UserNotifications types before pushing would catch both cheaply.
- A `Dictionary.Keys?` doesn't unify with an `[Any]` fallback in `?? []` — coalesce the dictionary itself (`(dict ?? [:]).keys`), not its `.keys` view, when chaining `??`.
- Session 6, run 2: **reordering #14 after #11/#9/#10/T2, out of the playbook's listed order.** #14 ("notification tap opens check-in") needs a check-in cover screen to route to, and that screen is #19 — much later, after capture/#20 etc. Building #14 now would mean inventing router/coordinator plumbing (what a "pending check-in" route even looks like) speculatively, ahead of what #19 will actually need — exactly the "design for hypothetical future requirements" CLAUDE.md warns against. #11 (Intention screen) is self-contained, slots directly into `RootView`'s already-built `.onboarding` branch, and needs no speculative plumbing, so it's the conservative choice per playbook §3. Flagging rather than silently reordering; #14 stays `todo`, picked up once #19 exists and there's a real destination to route to.
- `.backgroundTask(.appRefresh(_:))` (the SwiftUI/iOS 17+ replacement for manually calling `BGTaskScheduler.register`) was used for RUKI-015's design reasoning (not yet written into `RukiApp` — that's still `todo`, needs T2/#34 too) after a web search confirmed it replaces manual registration/casting entirely and removes the `BGAppRefreshTask`/`Sendable` casting risk that a hand-rolled `register(forTaskWithIdentifier:using:launchHandler:)` wrapper would have carried. `WebFetch`/`WebSearch` worked from this sandbox and are worth reaching for before guessing at current iOS API shapes (CLAUDE.md: "check rather than guess") — several fetches were blocked by the egress proxy (kodeco.com, swiftcrafted.dev, Apple's doc pages themselves) but `WebSearch` still surfaced enough corroborating third-party code samples to be confident.
